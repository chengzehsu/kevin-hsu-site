# 投遞追蹤後台與客製版本連結

## 要解決的問題

Kevin 正在求職，每家公司的職缺要求不同（例如流程改善、系統導入、AI 應用）。
目前全站只有一份文案，追蹤連結（`?s=代碼` → Umami）只能知道對方有沒有打開，
無法讓不同公司看到針對職缺調整過的重點，也沒有地方記錄投了誰、對方要什麼、給了哪一版。

## 使用者確認過的決定（2026-10-14）

- 後台要跟前台有關聯：追蹤連結決定對方看到哪一版。
- 採「全站共用，版本只覆寫 HR 第一眼看的欄位」（方案 A），不是整站文案分版本。
- 後台要顯示每個連結的開啟紀錄（Umami）。
- 後台系統用 PocketBase（已在 `backend/`，Zeabur 獨立服務）；只有 Kevin 能登入。
- 不要用 claude.ai Artifact，不要只在本機跑。
- 後台介面必須全中文（台灣用語）、沿用網站的設計語言，日常操作完全不需要進 PocketBase 內建的英文管理介面
  （使用者明確表示無法忍受該介面）；PocketBase 只當資料與登入的後端。

## 範圍

### 版本（variant）可覆寫的欄位，中英各一份

- 一頁履歷與首頁 hero 的 headline
- 履歷摘要（summary）與關鍵字（keywords）
- 核心能力卡：順序，以及每張卡的 statement／summary
- 每段經歷要突顯的 bullets（從既有 bullets 挑選與排序，可另加一條）
- 案例排列順序

其餘（案例頁內容、影片、數字、獎項）一律沿用主站，不分版本。

### 投遞（application）

公司、職位、職缺連結、職缺要求、狀態、投遞日、綁定的版本、追蹤代碼與網址、
寄出當下的網站版本（commit，自動帶入）、寄出的 PDF、備註。

### 前台行為

- 連結帶 `?s=代碼`（或已改寫成 `utm_source`）時，向後台的公開端點取得該代碼綁定版本的覆寫欄位，
  只回傳文案，不回傳公司名稱、備註等私人資料。
- 同一次瀏覽中換頁仍維持該版本（sessionStorage）。
- 取不到、逾時或代碼不存在時顯示主站內容，不能壞版、不能出現閃爍的內容替換。
- 沒帶代碼的訪客看到的永遠是主站。

### 後台

- 網站內的 `/admin/`（靜態頁，`noindex`、不在導覽、不進 sitemap），用 PocketBase 帳號登入。
- 兩個列表：版本、投遞。投遞旁顯示 Umami 開啟次數與最近一次開啟時間。
- Umami API 金鑰只放在 PocketBase 伺服器端（pb_hooks 代理），前端拿不到。
- 版本一旦綁定到已寄出的投遞就鎖定；要改就複製成新版本（對方看到的內容要是寄出當下的快照）。

## 已知風險與要求

- 中文字型是文案子集，覆寫文案可能用到子集外的字；要有不缺字的退路。
- 覆寫文案裡的數字要跟主站一致（+233%、+50%、+66% 等標準寫法），後台要提示不一致。
- 後台要能產生追蹤代碼並與 `pnpm utm` 的規則一致（代碼格式、不可用人名、重複代碼警告）。
- 靜態輸出、Zeabur 部署方式維持不變；網站服務不能因後台停機而無法瀏覽。
